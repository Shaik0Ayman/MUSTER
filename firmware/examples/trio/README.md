# trio — three ESP32s, one math task, PWM out, live dashboard

```
   ESP32-C6  (LEAD)  ──────── ESP-NOW (WiFi radio, channel 1) ────────┐
   • places each call                                                  │
   • WiFi access point "muster-trio"  →  dashboard at 192.168.4.1      │
   • PWM on GPIO18                                                     │
                                  ┌────────────────────────────────────┴───┐
                           ESP32 DevKit (WORKER)               ESP32 DevKit (WORKER)
                           • runs wave(step)                   • runs wave(step)
                           • PWM on GPIO2 (on-board LED)       • PWM on GPIO2 (on-board LED)
```

No CAN transceivers, no wires between boards: Muster runs over **ESP-NOW**
([`firmware/src/muster_link_espnow.h`](../../src/muster_link_espnow.h), described in
[`docs/LINKS.md`](../../../docs/LINKS.md)), a broadcast radio that behaves like a shared bus.
Just power the three boards.

> **Status: run on hardware** (2026-11-07, ESP32-C6 lead + two ESP32 DevKits). Join,
> placement, failover and rejoin worked, and the dashboard showed about 900 µs average
> compute time per call on a worker. Radio latency hasn't been measured yet. Details are in
> [What is and is not verified](#what-is-and-is-not-verified).

**What happens.** The lead keeps three calls in flight to `wave(step, 256)`, a 256-term
Fourier series computed in floating point. Muster's placement decides which worker runs
each call. The sum converges to a sawtooth, which the worker maps to a PWM duty and puts
on its pin, so each board's LED ramps up and down. The worker also returns its vital signs
(uptime, free heap, time taken, tasks run) with the answer, and the lead turns those into
the dashboard. Switch a worker off and the lead notices after about a second and sends the
work to the other one; switch it back on and it rejoins.

## Files

| Path | What |
|---|---|
| `muster_trio/muster_trio.ino` | **the demo**, one sketch for all three boards (role follows the chip: C6 = lead, otherwise worker) |
| `muster_trio/trio_task.h` | the math task and the result layout (host-tested) |
| `muster_trio/trio_lead.h`, `trio_worker.h`, `trio_board.h` | the two roles and the shared board glue |
| `muster_trio/dashboard.h` | the web page (one self-contained file, no internet needed) |
| `node_selftest/node_selftest.ino` | **per-board test**: chip info, PWM pin breathes, lists the other boards it can hear |
| `tools/trio_mock.py` | preview the dashboard on your PC with simulated data |
| `platformio.ini` | `worker_esp32`, `lead_c6`, `lead_esp32dev` (lead role on a classic ESP32) |

## Pins

| Board | PWM pin | Notes |
|---|---|---|
| ESP32 DevKit (worker) | GPIO2 | the blue on-board LED on most DevKits: visible with no wiring |
| ESP32-C6 (lead) | GPIO18 | the C6 DevKit's on-board LED is an RGB part, so wire an LED + 330 Ω from GPIO18 to GND, or probe it. `-DTRIO_RGB_LED` also mirrors the duty on the RGB LED (untested) |

Change with `-DTRIO_PWM_PIN=<n>`. These are example defaults, not taken from `boards.yaml`
(this example is hand-written, not generated by `muster-cli`).

## Run it

### 1. Test each board first (5 minutes)
Flash `node_selftest` to all three and open each serial monitor at 115200.

* the chip line prints, and the PWM pin **breathes** (LED fades up and down about once a second);
* every 2 s it prints `hear N other board(s)`. With all three powered you want `hear 2 … => RADIO OK` on **each** board.

If a board hears nobody, stop here: the demo cannot work until the radio check passes.

### 2. Flash the demo
With PlatformIO (from this folder):

```bash
pio run -e worker_esp32 -t upload --upload-port COMx     # run once per DevKit: the same image goes on both
pio run -e lead_c6      -t upload --upload-port COMy     # the C6
```

With the Arduino IDE: copy the repo's `firmware/` folder to `Documents/Arduino/libraries/Muster`,
install the **esp32 core 3.x** (needed for the C6), open `muster_trio/muster_trio.ino`, pick
*ESP32 Dev Module* for the DevKits and *ESP32C6 Dev Module* for the C6, upload.

The C6 DevKit has two USB-C ports. Use the one labelled **UART** (it has the USB-serial chip);
on the other one, set *USB CDC On Boot: Enabled* to see serial output.

### 3. Watch it
Join the WiFi **muster-trio** (password **muster123**) from a phone or laptop and open
**http://192.168.4.1/**. (Your phone may say "no internet": stay connected.)

* Worker serial: `node 87  joined  tasks run=…`. A worker that is **blinking** has not found the lead.
* Lead serial prints the same events the dashboard shows.
* Try it: unplug one worker. The page shows it as **lost**, the other worker takes all the calls.

### Preview the page without any boards
```bash
python3 tools/trio_mock.py        # then open http://localhost:8080/
```
The numbers are simulated (a worker drops out for 10 s every 40 s). It shows the page, not the boards.

## Settings (`-D` build flags)

`TRIO_CHANNEL` (1), `TRIO_AP_SSID`, `TRIO_AP_PASS` (≥ 8 chars), `TRIO_CALL_MS` (50),
`TRIO_PWM_PIN`, `TRIO_ROLE_LEAD` / `TRIO_ROLE_WORKER` (force a role).

## What is and is not verified

Verified (2026-11-04):
* `make -C firmware/test` and `… cpp`: `test_espnow_link` (ring, packets, a lead + two workers on a
  lossy broadcast medium, a node-ID change, a worker leaving) and `test_trio_task` (the series
  against its closed form, result encoding).
* `worker_esp32`, `lead_esp32dev` and `selftest_esp32` **compile** (Arduino-ESP32 2.0.17; rechecked 2026-11-07).
* The dashboard renders and updates in Chrome, light and dark, driven by the mock.

**Run on hardware (2026-11-07, ESP32-C6 lead + two ESP32 DevKits):** the workers joined, the lead
placed calls on both, the dashboard was served by the C6 from its access point while ESP-NOW ran (so
SoftAP + ESP-NOW coexist on the lead), a worker that was switched off was declared lost and the other
took the calls, and it rejoined when powered back. The dashboard's average task time per worker was
**≈ 900 µs**. That is the worker's compute time for `wave(step, 256)` (`busy_us`), not the radio
round trip. Details: [`docs/TESTING.md`](../../../docs/TESTING.md#hardware-results).

**Not verified:** the radio round-trip latency and failover time (not measured), the PWM output,
`node_selftest`, `-DTRIO_RGB_LED`, and the other timings in this file. On the machine used for
development, `lead_c6` and `selftest_c6` don't build with PlatformIO Core 6.2.0.post1: the pioarduino
platform needs 6.2.0 or newer (`pio upgrade`). CI installs a current PlatformIO and builds them. If ESP-NOW from the lead's WiFi
AP interface misbehaves, `lead_esp32dev` runs the lead role on a classic ESP32 as a fallback.

Things to know:
* The C6 has **no FPU**, so `sinf` is software there: the lead would take far longer per call than a
  worker. Placement penalises the lead, so it only computes when no worker is alive.
* Tasks run inside `muster_poll()` and the web server shares the lead's loop; both are short here.
  A long page request could delay a heartbeat.
* A call that moves to another board after its first board went silent can run twice (at-least-once,
  see *Guarantees and limits* in the top-level README); `wave` is a pure function, so that is harmless.
